Shrinking the Keys: Compact p-Party FSS with a Non-linear Decoder

Posted 12 August 2024 · ~25 min read

function secret sharingDPFDCF seed-homomorphic PRGPPML

Based on joint work with Sikhar Patranabis and Debdeep Mukhopadhyay — Compact Key Function Secret Sharing with Non-linear Decoder, IACR Communications in Cryptology, Vol. 1, Issue 2 (2024). This post is the intuition; the paper carries the constructions and the proofs.

Function secret sharing has a two-party problem. Almost every efficient construction in the literature splits a function between exactly two servers, because that is where the beautiful $O(n)$-sized keys live. The moment you want three servers, or five, or ten — which is exactly what you want if your threat model dislikes trusting a single pair of machines — key sizes stop being logarithmic and start being measured in megabytes.

This paper asks a narrow question with a practical edge: can we make those $p$-party keys smaller if we are willing to give the decoder a little more work to do? The answer turns out to be yes, and the price is unusually cheap — one or two comparisons at the very end of the protocol, performed by a party that was going to add up the shares anyway.

The setting, in one picture

An FSS scheme for a function class $\mathcal{F}$ takes a function $f$ and splits it into $p$ succinctly described functions $f_1,\dots,f_p$ such that $\sum_i f_i = f$, and such that any $p-1$ of them together tell you nothing about $f$. Each server gets one share, evaluates it on a common input, and sends back a partial result. Somebody adds the partials up and recovers $f(x)$ — without any single server ever learning which function it was helping to compute.

Two function classes carry most of the practical weight. A distributed point function (DPF) shares the function $f_{\alpha,\beta}$ that outputs $\beta$ at the single input $\alpha$ and the identity everywhere else. A distributed comparison function (DCF) shares $f^{<}_{\alpha,\beta}$, which outputs $\beta$ on every input at or above a threshold $\alpha$. DPFs power private information retrieval, anonymous messaging, and distributed ORAM; DCFs are the workhorse behind secure comparison, and therefore behind every $\mathsf{ReLU}$ in a privacy-preserving neural network.

Why p parties at all

Two-party FSS has keys of size $O(\lambda n)$ — wonderfully small. But it forces you to bet the entire protocol on two servers not colluding. Spreading the trust over $p$ servers weakens that assumption to "at least one of $p$ is honest", which is a far easier thing to arrange in the real world across jurisdictions, vendors, or organizations. The catch is that the known $p$-party constructions pay for it in key size.

Where the megabytes come from

The naive $p$-party construction just additively secret-shares the entire evaluation table: $|\mathbb{G}| \cdot 2^n$ bits per party. Hopeless for any real domain. The standard fix, going back to Boyle, Gilboa and Ishai (Eurocrypt 2015), is to fold the one-dimensional table into two dimensions — $\mu$ columns by $\nu$ rows — so that a key only has to describe a row vector and a column vector rather than the whole grid.

That reshaping is where the schemes differ, and where the cost lives. In BGI15, built from plain PRGs, every row needs $2^{p-1}$ seeds, because the correction machinery has to work for every subset of parties. Riposte (S&P 2015) improved matters by switching to a seed-homomorphic PRG, which cuts the count to two vectors of row length plus one of column length. Our construction pushes it to one seed per row, and moves the correction words out of the secret key entirely.

Concretely, in megabytes

Asymptotics hide the sting, so take a plausible configuration: $p = 5$ parties, domain $n = 32$, an evaluation table split evenly into $2^{16}$ rows and $2^{16}$ columns, security parameter $\lambda = 256$, group size $|\mathbb{G}| = 256$.

For the comparison function the gap is not a constant factor but an exponential one. The only prior $p$-party DCF, again from BGI15, generates $q^{p-1}$ seeds per row, where $q$ is the order of the group the seeds are drawn from. Our DCF keeps the same share size as our DPF and pays only a $3\times$ larger public parameter. That is the difference between "a footnote in a theory paper" and "something you can actually deploy in a neural network layer".

The one gadget you need: a seed-homomorphic PRG

Everything hinges on a pseudorandom generator whose seed space is a group and whose output space is a group, such that

$\mathsf{G}(s_1 \oplus s_2) \;=\; \mathsf{G}(s_1) \otimes \mathsf{G}(s_2).$

There is an almost embarrassingly simple instantiation. Take a cyclic group $\mathbb{G}$ of prime order $q$ where DDH is hard, fix generators $g_1,\dots,g_4$, and define $\mathsf{G}(s) = (g_1^{s}, g_2^{s}, g_3^{s}, g_4^{s})$. Componentwise multiplication of $\mathsf{G}(s_1)$ and $\mathsf{G}(s_2)$ gives $(g_i^{s_1+s_2})_i = \mathsf{G}(s_1+s_2)$, and the homomorphism holds by inspection.

Why this is the whole trick

Additive secret sharing lives in the exponent. If the $p$ servers hold shares $sh_1,\dots,sh_p$ of a seed $s$, then each can locally compute $\mathsf{G}(sh_i)$, and the componentwise product of those outputs is exactly $\mathsf{G}(s)$ — without anyone ever reconstructing $s$. One seed per row suddenly suffices, because the sharing structure does the work that $2^{p-1}$ separate seeds were doing before.

A worked example: the DPF, with four bits and three parties

Take $f_{\alpha,\beta}: \{0,1\}^4 \to \mathbb{G}$ with $\alpha = 1001$, and three parties $P_1, P_2, P_3$. Split $\alpha$ down the middle: the first half $\gamma = 10$ names a row, the second half $\delta = 01$ names a column. The evaluation table has $\beta$ in exactly one cell.

$f_{1001,\beta}$00011011
00$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$
01$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$
10$1_\mathbb{G}$$\beta$$1_\mathbb{G}$$1_\mathbb{G}$

Key generation, in two moves

  1. Correction words. The dealer picks one seed $s_\gamma$ for the target row $\gamma = 10$, and computes, for every column $\delta'$, $$cw_{\delta'} = \begin{cases} \beta \otimes \mathsf{Inv}\!\left(\mathsf{G}^{(\delta')}(s_\gamma)\right), & \delta' = 01,\\[4pt] 1_\mathbb{G} \otimes \mathsf{Inv}\!\left(\mathsf{G}^{(\delta')}(s_\gamma)\right), & \text{otherwise.}\end{cases}$$ These four values $CW = (cw_{00}, cw_{01}, cw_{10}, cw_{11})$ are published. They are computed only for the target row, but nothing about them reveals which row that was.
  2. Seed shares. For every non-target row, the dealer hands the parties additive shares of $0_S$. For the target row $\gamma = 10$, it hands them shares of $s_\gamma$: $$sh_{1,j} \oplus sh_{2,j} \oplus sh_{3,j} = \begin{cases} s_\gamma, & j = 10,\\ 0_S, & \text{otherwise.}\end{cases}$$ Each party's key is just its column of shares — one group element per row.

Evaluation, and why it works

On input $x = (\gamma^*, \delta^*)$, party $P_i$ looks up its share for row $\gamma^*$ and outputs a single group element: $\mathsf{PartComp}_i = \mathsf{G}^{(\delta^*)}(sh_{i,\gamma^*})$. The decoder multiplies the three partials together with the public correction word:

$\mathsf{Res} = cw_{\delta^*} \otimes \mathsf{PartComp}_1 \otimes \mathsf{PartComp}_2 \otimes \mathsf{PartComp}_3 = cw_{\delta^*} \otimes \mathsf{G}^{(\delta^*)}\!\left(sh_{1,\gamma^*} \oplus sh_{2,\gamma^*} \oplus sh_{3,\gamma^*}\right).$

Three cases cover everything:

InputRow / columnShares reconstruct toResult
$x = 1101$wrong row$0_S$$cw_{01}$ → decoder outputs $1_\mathbb{G}$
$x = 1001$right row, right column$s_\gamma$$\beta \otimes \mathsf{Inv}(\mathsf{G}^{(01)}(s_\gamma)) \otimes \mathsf{G}^{(01)}(s_\gamma) = \beta$
$x = 1011$right row, wrong column$s_\gamma$$1_\mathbb{G}$

Notice what carries the security. Two parties pooling their shares see nothing: additive sharing hides $s_\gamma$ until all $p$ pieces are present. The correction words are public, but recovering $\beta$ from $cw_{\delta'}$ would mean inverting $\mathsf{G}$ — that is the discrete log problem in $\mathbb{G}$.

One seed per row instead of $2^{p-1}$, and the corrections moved from every key into a single public table. That is the whole DPF improvement.

The comparison function breaks the pattern

Now try to run the same construction for $f^{<}_{1001,\beta}$, which outputs $\beta$ on every input from $1001$ upward. Write out its table and the difficulty is visible immediately.

$f^{<}_{1001,\beta}$00011011
00$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$all identity
01$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$$1_\mathbb{G}$all identity
10$1_\mathbb{G}$$\beta$$\beta$$\beta$mixed — the awkward one
11$\beta$$\beta$$\beta$$\beta$all $\beta$

A DPF table has exactly one interesting row. A DCF table has three kinds of row: rows entirely below the threshold, rows entirely above it, and the single row where the threshold falls in the middle. One correction word can no longer describe them all, and once you have three correction words, the decoder faces a question it never had to answer before: which one of them was the right one?

Where the linear approach dies

Riposte's reconstruction works because there is exactly one correction word $v[\delta]$, so the partial computation $g[\delta] + b[\gamma]\,v[\delta]$ stays linear and the shares simply add up. Introduce three correction words and the parties would have to compute against all three independently — but only one combination yields the correct evaluation, and addition alone cannot tell you which. Something has to compare.

That is the concession the paper makes, and it names it in the title: the decoder becomes non-linear. Instead of summing partial results, it sums them a few different ways and picks the answer by comparison. In exchange, the key size collapses from $q^{p-1}$ seeds per row to the same one-seed-per-row structure as the DPF.

Three correction words, three kinds of row

The dealer now samples three seeds and binds each to a row type: $s_{\gamma_1}$ for the all-identity rows, $s_{\gamma_2}$ for the mixed row, $s_{\gamma_3}$ for the all-$\beta$ rows. Correction words $CW_1, CW_2, CW_3$ are built against them the same way as before. Seed shares follow the row's type — shares of $0_S$ for rows below the threshold, of $s_{\gamma_2}$ for the mixed row, of $s_{\gamma_3}$ for rows above it.

Each party now returns two partial computations rather than one: $\mathsf{PartComp}_{i,1}$ on column $\delta^*$, and $\mathsf{PartComp}_{i,2}$ on the neighbouring column $\delta^* \pm 1$. The second one is what lets the decoder distinguish "this row is entirely $\beta$" from "this row happens to contain $\beta$ at this column".

Walking the four cases makes the logic concrete. For $x = 0110$ the row lies below the threshold, the shares reconstruct $0_S$, and $\mathsf{Res}_1$ matches $cw^1_{\delta^*}$ straight away — output $1_\mathbb{G}$, done in one comparison. For $x = 1101$ the row is above the threshold, so the shares rebuild $s_{\gamma_3}$; $\mathsf{Res}_1$ fails, but $\mathsf{Res}_2$ and $\mathsf{Res}_3$ agree because every column of that row embeds $\beta$. For inputs landing in the mixed row — $x = 1000$ and $x = 1010$ — neither test fires, and only $CW_2$ resolves the cell correctly.

An interval function comes almost free at this point: chain two DCFs and the key size doubles.

What it buys: a $\mathsf{ReLU}$ you can afford

The motivation for shrinking DCF keys is not aesthetic. In a privacy-preserving inference system, a single neural-network layer evaluates thousands of comparison functions, one per activation. Each of them needs its own FSS key sitting on every server. Multiply BGI15's $q^{p-1}$-seeds-per-row by a few thousand activations and the storage bill alone rules the approach out.

The paper prototypes the obvious application: a pre-trained model additively shared across $p$ servers, and a client who wants inference without handing over its input. Linear layers use Beaver triples; non-linear layers use our DCF through the standard offset-function trick, so that servers only ever see masked values.

$\mathsf{ReLU}$ decomposes into two comparison functions, so each activation consumes two DCF keys with $(\beta_0, \beta_1) = (1, -r)$ when the input exceeds the mask and $(0,0)$ otherwise. The client's extra burden over a conventional FSS decode is two comparisons — addition and comparison are exactly the operations a thin client can be expected to run locally.

The honest caveat

Function privacy needs a trusted decoder

An adversary who can see every party's partial computations can probe the scheme: $2^{n/2}$ queries, one per row of the evaluation table, are enough to spot the target row from the aggregated values. We patch this by masking each party's partial output with a share of an output mask $r_{\mathsf{out}}$ that only the decoder holds, which pushes the adversary back to needing all $2^n$ inputs. That is fine for the application here — the client is the decoder and has every reason to be trusted with its own query — but it is not universal. Achieving unconditional function privacy for FSS with non-linear decoding is left open.

Two other boundaries worth stating plainly. The construction is public-key: it needs a seed-homomorphic PRG, so evaluation is group exponentiation rather than a few AES calls, and it inherits a discrete-log (or lattice) assumption that symmetric-key FSS does not need. And the comparison the decoder performs is not free of structure — it is what makes the scheme non-linear, which means it does not compose into every protocol that expected plain additive reconstruction.

Takeaways

  • Seed-homomorphic PRGs let $p$-party FSS carry one seed per row instead of $2^{p-1}$, because additive sharing already lives in the exponent.
  • Pushing correction words out of the secret key and into a public parameter is safe under discrete log, and removes a whole vector from every party's key.
  • The comparison function's evaluation table has three row types, not one — which is precisely why linear reconstruction cannot survive the jump from DPF to DCF.
  • Letting the decoder compare rather than only add turns an $O(q^{p})$ key blowup into the same compact structure as the DPF, at a cost of at most two comparisons.
  • Concretely: 32 MB → 6 MB → ~4 MB for a five-party DPF, and the first $p$-party DCF small enough to put thousands of them in a neural-network layer.
