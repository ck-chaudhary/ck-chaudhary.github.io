Who Guards the Guard? Reverse Firewalls That Survive a Hardware Trojan

Posted 26 September 2025 · ~25 min read

reverse firewallssubversionhardware Trojans private circuitsOP-TEE

Based on joint work with Nimish Mishra, Suvradip Chakraborty, Satrajit Ghosh and Debdeep Mukhopadhyay — TERRA: Trojan-Resilient Reverse-Firewall for Cryptographic Applications, ESORICS 2025. This post is the intuition; the paper carries the definitions, the proofs, and the implementation details.

Cryptographic reverse firewalls exist because of an uncomfortable thought experiment: what if the machine running your protocol is working against you? Not the network, not the other party — your own hardware, subverted somewhere between the fab and your desk, quietly steering its "random" choices so that every message you send leaks a little of your secret key.

Mironov and Stephens-Davidowitz gave that thought experiment a defence at Eurocrypt 2015. Put a small, separate box on the wire. Let it re-randomize everything leaving the machine. If it does its job, the subverted host loses its covert channel, and the protocol's guarantees survive even though the host does not deserve them.

Our paper asks the question that follows immediately, and that the literature had left alone: where did the firewall itself come from?

Reverse firewalls in one picture

The property that matters is exfiltration resistance. Informally: an adversary who compromised Alice's machine and watches the wire should not be able to distinguish the firewall's output from the output it would get if Alice were running honestly. If that holds, the covert channel is gone, whatever the subverted code was trying to do with it.

Concretely, in an oblivious transfer

In the OT protocol from the original RF paper, Bob sends $(g, c, d = g^{y}, h = c^{y}g^{b})$. Bob's firewall picks fresh $\alpha, x', y'$ and rewrites this as $g' = g^{\alpha}$, $c' = c^{\alpha}g'^{x'}$, $d' = d^{\alpha}g'^{y'}$, $h' = h^{\alpha}c^{\alpha y'}d^{\alpha x'}g'^{x'y'}$ — a fresh, correctly distributed tuple encoding the same choice bit. On the way back it de-randomizes, $e'_i \leftarrow e_i / u_i^{y'}$, so Bob still decrypts the message he asked for. Alice's firewall does the symmetric thing to $(u_i, e_i)$. Every value on the wire has been re-drawn; a subverted Bob has nowhere to hide a bit.

The question nobody was asking

Every guarantee above is a statement about a specification. It says: if a box computes this re-randomization function, exfiltration resistance holds. It says nothing about the box.

And notice the awkward position the firewall occupies. It must be physically separate from Alice's machine, or it would be subverted along with it. It is small, special-purpose hardware. It is, in other words, exactly the kind of component you buy from somebody else — designed by one vendor, fabricated by another, integrated by a third. The trust model that motivates reverse firewalls in the first place, a supply chain you cannot vouch for, applies with full force to the firewall itself.

We build the firewall because we do not trust the manufacturer of the host. Then we buy the firewall from a manufacturer.

So: suppose the firewall contains a hardware Trojan. Not a broken firewall — one that computes the right function almost always, and misbehaves on a rare trigger, which is what real Trojans are designed to do. What happens to exfiltration resistance?

A Trojan turns the guard into the leak

The failure is not subtle once you see it. The firewall's whole job is to replace the adversary-chosen randomness with randomness the adversary cannot predict. A Trojan sitting in the re-randomization path can simply decline to do that — reuse a nonce, bias a value, pass a message through untouched on the trigger condition. The output still looks like a valid protocol message. It is only the distribution that has been quietly restored to the one the subverted host wanted.

This is worse than an ordinary implementation bug for two reasons. First, the party being protected has no way to detect it: Alice's machine is already compromised, and the transcript looks fine to everyone. Second, the firewall was designed to be untrusted, so nobody put integrity machinery inside it. The security argument silently assumed a component that behaves according to spec — in a setting whose entire premise is that components do not.

The claim, stated carefully

A Trojan-affected reverse firewall implementation can break exfiltration resistance, and with it the RF's security guarantees collapse entirely. Nothing in the prior definitions rules this out, because those definitions quantify over protocol transcripts, not over circuits.

Trojan-resilient reverse firewalls

The repair starts with the definition. We extend the standard RF notion with an additional Trojan resilience property, giving Tr-RF, and correspondingly strengthen the two guarantees you care about into their robust forms:

  • Robust exfiltration resistance — exfiltration resistance holds even when the firewall's circuit contains Trojans, up to the tolerated threshold.
  • Robust security preservation — the underlying protocol's security is preserved under the same condition.

Defining the property is the easy half. The hard half is that you cannot inspect your way to it: a Trojan with a rare trigger passes every functional test, and imaging every gate of every chip you buy is not a deployment strategy. What you need is a construction that keeps working even if some of its components are malicious, without knowing which.

Borrowing a hammer: Private Circuits III

Dziembowski, Faust and Standaert (CCS 2016) built exactly that hammer, for a different nail. Their Private Circuits III compiler takes a circuit and produces a Trojan-resilient version by combining three ideas: split the computation across many small components so that no single one sees anything meaningful, replicate each component and take a majority vote, and use testing amplification — randomly test components often enough that a Trojan which misbehaves often enough to matter is caught, while one that misbehaves rarely enough to escape testing is too rare to help the adversary.

The architecture that comes out is a master circuit surrounded by replicated mini-circuits. The master handles secret-sharing, dispatch, and reconstruction. The mini-circuits do the arithmetic on shares, in triplicate, under a vote.

Rebuilding Bob's firewall out of shares

Applying this to the OT firewall is where the work is. Every operation the firewall performed in the clear must become an operation on secret shares. Take the re-randomization of $(g, c, d, h)$:

  1. Master shares the inputs. It samples $\alpha \in \mathbb{Z}_p^{*}$ and $(x', y') \leftarrow \mathbb{Z}_p^2$, secret-shares $g, c, d, h$ as $[g]_p, [c]_p, [d]_p, [h]_p$ among the mini-circuits, and distributes $\alpha, x', y'$.
  2. Mini-circuits exponentiate. Each invokes the public exponentiation protocol — $\mathsf{Exp}([g]_p, \alpha)$ and friends — to get $[g^{\alpha}]_p, [c^{\alpha}]_p, [d^{\alpha}]_p, [h^{\alpha}]_p$, then again for the cross terms $[g^{\alpha x'}]_p, [g^{\alpha y'}]_p, [c^{\alpha y'}]_p, [d^{\alpha x'}]_p, [g^{\alpha x' y'}]_p$.
  3. Mini-circuits multiply. Secure multiplication combines those into shares of $c'$, $d'$ and $h'$ — $h'$ needing one further $\mathsf{Mult}$ over the results of the previous two.
  4. Master reconstructs. $g' = \mathsf{Reconstruct}([g^{\alpha}]_p)$, and likewise for $c', d', h'$ — the same four values the plain firewall would have produced, now computed by a circuit no single component of which ever saw them.

The return path works the same way. To produce $e'_i = e_i / u_i^{y'}$, the master shares $e_0, e_1, u_0, u_1$; the mini-circuits run $\mathsf{Exp}$ to get $[u_i^{y'}]_p$, a private inverse protocol $\mathsf{Inv}$ to get $[u_i^{-y'}]_p$, and $\mathsf{Mult}$ to reach $[e'_i]_p$; the master reconstructs. Alice's firewall is rebuilt along the same lines, including the $g = 1_{\mathbb{G}}$ abort check, which stays in the master.

Why this restores the guarantee

A Trojan in a mini-circuit is now in a bad position. It sees only shares, so it cannot tell which value it is corrupting or what the protocol state is; it is replicated, so any deviation is outvoted; and testing amplification bounds how often it can act without being detected. The paper proves the two robust properties formally — robust exfiltration resistance and robust security preservation for both the coin-tossing and OT instantiations, via simulation-based arguments that reduce to the underlying RF's guarantees.

From paper to Raspberry Pi

Private Circuits III comes with assumptions that are easy to write down and awkward to obtain: components that are genuinely isolated, a master circuit that can be trusted to share and reconstruct, and a testing procedure that a Trojan cannot detect and evade. A construction that needs those assumptions is only as real as your ability to supply them.

So we built it. The Tr-RF for coin tossing and for oblivious transfer is implemented on the Open Portable Trusted Execution Environment (OP-TEE) over ARM TrustZone, on Raspberry Pi 3 and 4. TrustZone's secure/normal world split gives the isolation between master and mini-circuits; trusted applications give the mini-circuits their separation from one another; remote attestation — hardware measurements plus application state, signed by the OEM — gives a handle on whether the code that is running is the code that was meant to run.

That last sentence is worth dwelling on. Reverse firewalls had been studied for a decade — for message transmission, for actively secure MPC, for OT extension, for PAKE — and the constructions were sound. But nobody had built one. Which is precisely how a gap like the Trojan question stays invisible: it is not visible from inside a specification, only from the point where you have to ask a manufacturer for a box.

What this changes

  • An untrusted-by-design component still has to be manufactured by somebody. If your threat model admits subverted hardware, it admits a subverted firewall, and the original guarantees do not survive that.
  • Exfiltration resistance is a property of a circuit, not only of a transcript. Tr-RF makes that explicit with robust exfiltration resistance and robust security preservation.
  • Private Circuits III turns out to be the right tool: share, replicate, vote, test. The translation cost is real — every clear-text operation becomes a protocol over shares — but it is a compilation, not a redesign.
  • OP-TEE and TrustZone can supply the isolation assumptions that PC-III needs, which is what takes the construction from "provable" to "running on a Pi".
  • More generally: protocol specifications should be evaluated in implementation-specific contexts. Some security properties simply cannot be stated, let alone checked, at the level of abstraction where we usually prove them.

The natural next question is what else leaks once you look at the physical layer rather than the transcript — which is where our follow-up work on structural leakages in PC-III goes, mounting a correlation power attack on TrustZone's shared power rails against a live deployment of exactly this construction. But that is another post.
